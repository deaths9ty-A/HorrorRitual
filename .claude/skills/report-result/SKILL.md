# รายงานผลตามที่ตรวจจริง

**เหตุผล:** เจ้าของเป็นผู้ตัดสินว่างานใช้ได้ รายงานจึงเล่าสิ่งที่เกิดขึ้นจริงและส่งการตัดสินให้เจ้าของ

## วงตรวจก่อนส่ง (คัดลอกไปติ๊ก)
```
- [ ] 1 รันคำสั่งตรวจในรอบเดียวกับที่รายงาน และอ่านผลเต็ม (คำสั่งอยู่ใน CLAUDE.md หัวข้อ "คำสั่งตรวจงาน")
- [ ] 2 สแกนร่างหาคำ ผ่าน / ใช้ได้ / ทำแล้ว / น่าจะ / ควรจะ แล้วแทนด้วยสถานะจริง
- [ ] 3 เทียบกับบรีฟที่เจ้าของยืนยัน: ทุกช่องของบรีฟมีผลตอบ
- [ ] 4 ค่าต่ำกว่าเกณฑ์ของเจ้าของ (เช่น FPS ต่ำกว่า 60) ขึ้นเป็นบรรทัดแรกพร้อมตัวเลข
- [ ] 5 ส่งรายงาน
```
ข้อไหนในวงตรวจยังไม่ผ่าน ให้แก้แล้ววนตรวจใหม่ก่อนส่ง

## รูปแบบต่อหนึ่งข้อ
```
<ข้อ> · สถานะ: <สร้างแล้ว | รันเทสแล้ว | ถ่ายภาพแล้ว | รอเจ้าของเล่น>
ใครตรวจ: <Claude | เจ้าของ | สปาร์ค>
วิธีตรวจ: <คำสั่ง / สคริปต์ / ภาพ>
ยังไม่ได้ลอง: <รายการ>
ความมั่นใจ: <อ่านจากเอกสาร | เคยรันแล้ว | เดา ยังไม่ได้ลอง>
```

## หลักเขียน
- สถานะของงานที่เจ้าของยังไม่ได้เล่นคือ **"รอเจ้าของเล่น"** คำว่า "ผ่าน" "ใช้ได้" "ทำแล้ว" เป็นคำของเจ้าของ ใช้เมื่ออ้างถึงสิ่งที่เจ้าของพูดเอง
- เทสที่ Claude เขียนมีหน้าที่บอกว่า "ระบบยังไม่พัง" เขียนตามนั้น แล้วบอกว่าความสนุกและความน่ากลัวต้องให้เจ้าของเล่น
- เซสชันคลาวด์ไม่มี Godot โค้ดที่เขียนในคลาวด์มีสถานะ "ยังไม่ได้รัน" พร้อมคำสั่งที่เจ้าของรันบนเครื่องได้
- งานที่สปาร์คส่งคืน: ผมตรวจว่าตรงบรีฟไหมแล้วเขียนผลตรวจแยกจากผลของสปาร์ค เจ้าของเป็นผู้ตัดสินสุดท้าย
- ค่าที่ Claude ตั้งเอง ระบุซ้ำในรายงานว่า "ค่าเริ่มที่ Claude ตั้ง"

## ท้ายรายงาน
เขียนรายการ **"ควรลองอะไรตอนเล่น"** 3–5 ข้อ และถามเจ้าของว่าจะแก้ตรงไหนหรือไปชิ้นถัดไป
