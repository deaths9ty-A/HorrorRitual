# ชุดทดสอบสกิล (3 ข้อต่อสกิล)

> **สถานะ: ยังไม่ได้รันทดสอบ** · ชุดนี้เขียนโดย Claude ไว้ระบุว่าแต่ละสกิลควรทำอะไร ไม่ใช่หลักฐานว่าสกิลดี เจ้าของตัดสินจากการใช้จริง
> T1 T3 T7 มาจากเคสพลาดจริงของเจ้าของ (SK-05) · ที่เหลือเป็นตัวอย่างสมมติที่ Claude เขียน
> รูปแบบ: ผู้ใช้พิมพ์ → พฤติกรรมที่คาดหวัง

## intake
- **T1 ตีความผิด (เคส 1)** · "ทำเสียงเดินให้ด้วย เบา ๆ" → ผมเข้าใจว่า A (เสียงเท้าผู้เล่น) หรือ B (เสียงเท้ามอน)? ถามหนึ่งข้อ ยังไม่สร้างอะไร
- **T2 หลายเรื่องปน** · ข้อความสามเรื่องสลับลำดับ มีคำว่า "อันนั้น" → แยกสามรายการ ตามคำอ้างอิงให้ครบ ติดป้ายความมั่นใจ จดลง docs/office พร้อมต้นฉบับ
- **T3 บรีฟไม่ครบ (เคส 2)** · "ทำที่ซ่อนให้หน่อย" → บรีฟ 7 ช่อง ช่องว่างถามหรือเติมเป็น "ค่าเริ่มที่ Claude ตั้ง" จบด้วย `รอคำว่า "ตรง"`

## think-first
- **T4 โจทย์กว้าง** · "อยากได้มอนที่น่ากลัว" → 2–3 ทางพร้อมภาพ ข้อดี ข้อแลก กลับตัวได้ไหม + ข้อแนะนำหนึ่งข้อ + เรื่องที่ยังเปิดอยู่ท้ายคำตอบ
- **T5 ลังเล** · "ยังไม่รู้จะเอายังไงดี" → ให้ค่าเริ่มต้น "ลองก่อนแล้วเปลี่ยนได้" พร้อมสัญญาณที่บอกว่าควรเปลี่ยน
- **T6 เรื่องใหม่แทรก** · กลางงานเสียง เจ้าของพูดถึงด่านใหม่ → จดเป็น #จอดไว้ แล้วถามว่า "คุยตอนนี้หรือจอดไว้ก่อน"

## piece-spec
- **T7 ไม่ออกแบบระบบล่วงหน้า (เคส 3)** · ชิ้นใหม่ "ที่ซ่อน" → สเปกมี "โครงระบบ" (ไฟล์ โหนด จุดต่อกับของเดิม ขั้นสร้าง 3–6 ขั้นพร้อมวิธีตรวจ) ก่อนโค้ด จบด้วย `รอคำว่า "ทำ"`
- **T8 งานเล็ก** · "ปรับความเร็วเดินเป็น 3.5" → สเปก 3 บรรทัด (ทำอะไร · ไฟล์ที่แตะ · วิธีตรวจ)
- **T9 กระทบงานเจ้าของ** · งานที่ต้องแตะฉากที่เจ้าของแก้แล้ว → ช่อง "งานเดิมที่กระทบ" ระบุไฟล์ และเลือกสร้างไฟล์ใหม่ข้างไฟล์เดิมหรือถามก่อน

## report-result
- **T10 เขียนโค้ดในคลาวด์** · สถานะ "ยังไม่ได้รัน" + คำสั่งที่เจ้าของรันบนเครื่องได้
- **T11 FPS ต่ำกว่าเกณฑ์** · FPS วัดได้ 52 → บรรทัดแรกของรายงานบอก "FPS 52 ต่ำกว่าเกณฑ์ 60" พร้อมวิธีวัด
- **T12 ร่างมีคำว่า "ผ่านแล้ว"** · วงตรวจแทนด้วย "รอเจ้าของเล่น" และระบุว่าใครตรวจอะไร
